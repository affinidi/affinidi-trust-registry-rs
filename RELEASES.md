# Releases

What operators deploy is a **release**, named by its `major.minor` version
(`0.27`, `0.28`, …). It is cut from `nightly`, stabilised and patched on its own
branch for as long as it is supported, and published from there as crates on
crates.io (`trust-registry`, `trql-client`) and a tag. Patches
(`0.27.1`, `0.27.2`, …) only ever happen on the release branch. The other
workspace members (`trqp`, a placeholder; `test-client`;
`test-trust-registry`) are `publish = false`; the `trqp` versions already on
crates.io are left as they are.

This follows the branching model of `affinidi-messaging-mediator` (and, before
it, `affinidi-webvh-service` and verifiable-trust-infrastructure). Every crate
in the workspace carries the release's version (lockstep).

The workflows are thin callers of `affinidi/pipeline-rust`'s release-branch
actions (`release-cut`, `release-prep`, `release-tag`, `release-publish`,
`release-backport`, `release-nightly`, `release-branch-rules`,
`release-guards`), which carry the scripts. A maintainer may still cut with a
local script as a fallback (see Cut below).

Every `uses:` in `.github/workflows/` names a commit SHA, with the branch or
tag it came from in a comment, so a change in `pipeline-rust` or a
third-party action reaches this repository's release and publish jobs only
through a PR here that moves the SHA. To pick up a `pipeline-rust` change,
replace each `affinidi/pipeline-rust/...@<sha>` with the new commit in one PR.
(The reusable `checks-no-test.yaml` still calls its own nested workflows by
branch; that is pinned inside `pipeline-rust`.)

## Branches

```
feature/*  ──PR──▶  main  ──(nightly.yml: last fully green commit)──▶  nightly
                                                                          │
                          release/0.27 ◀── cut ───────────────────────────┤
                          release/0.28 ◀── cut ───────────────────────────┘
```

| Branch | What it is | Written by |
|---|---|---|
| `main` | Active development. Every PR lands here first. Carries the *next* release's version (`0.28.0` once `release/0.27` is cut) and publishes nothing. | PRs |
| `nightly` | The newest `main` commit on which **every** `checks.yaml` job passed. Fast-forward only. Releases are cut from here, never from `main`'s tip. | `nightly.yml`, daily at 02:00 UTC |
| `release/<major.minor>` | One release, from its cut to its end of life. Takes backported fixes only. | Backport and prep PRs |
| `feature/*`, `fix/*` | Short-lived work. | Anyone |

## Versions and tags

The workspace is versioned in lockstep: `[workspace.package] version` in the
root `Cargo.toml` is the version of every crate (`version.workspace = true`),
and every internal dependency requires exactly that version
(`{ path = "…", version = "0.27.0" }`). Nobody edits either by hand; the
release tooling moves them together, and the `release guards` job in
`checks.yaml` fails a tree where they disagree.

On a release branch the current version is its `RELEASE` file; the tag is `v`
+ that. `RELEASE` exists on release branches only.

| Step | `RELEASE` | Tag | Crates (crates.io) |
|---|---|---|---|
| **Cut** `release/0.27` from `nightly` | `0.27.0-rc.0` | `v0.27.0-rc.0` (prerelease) | set to `0.27.0`, not published |
| **Stabilise** — backport fixes; each prep is another candidate | `0.27.0-rc.1`, … | `v0.27.0-rc.1`, … (prerelease) | — |
| **GA** | `0.27.0` | `v0.27.0` | publish `0.27.0` |
| **Patch** as fixes are backported | `0.27.1`, `0.27.2`, … | `v0.27.1`, … | publish `0.27.N` |
| **EOL** — marked in the table below; the branch stays, read-only | — | — | — |

`main` never publishes and never edits the version: the cut moves it to the
next minor. A patch never changes a public API in a breaking way — the
`semver (patch-compatible)` job runs `cargo semver-checks --release-type patch`
on every PR into a release branch — and a fix that needs a break stays on
`main` for the next release.

Up to `0.26.0`, every merge to `main` published from `main` through
`affinidi/pipeline-rust`'s release workflow, tagged `trust-registry-v…`.
`0.27.0` is the first release from a release branch, tagged `v0.27.0`.

## Schedule

Generated from the `v*` tags by `scripts/release_schedule.py`; nobody edits
it. Each tag the release tooling creates (a cut's `rc.0`, an rc, a GA, a
patch), and a daily run, starts `release-schedule.yml`, which regenerates the
table on `main` and opens a `docs(releases): update the release schedule` PR
from the `release-schedule` branch for a maintainer to merge. A PR into
`main` that changes RELEASES.md or the generator must leave the table
matching the tags (the `release schedule` check). Dates are UTC: a tag's date
is that of the commit it names. A cut that never went GA reads `superseded`
once a newer release is GA, and Latest ignores an rc of a patch.

## Support

**The newest two GA minor releases, N and N-1, are supported — however
short-lived.** This is the commitment, and it is deliberate: support follows
the GA releases, not the calendar. When a release goes GA it becomes N, the
previous N becomes N-1, and the release that was N-1 reaches end of life that
day.

- **What "supported" means.** Fixes for security problems and for defects
  that break a deployment are backported to the release's branch and shipped
  as a patch release (`0.N.x`). Features, refactors and dependency upgrades
  that are not themselves such a fix are never backported. Release
  candidates, `main` and `nightly` are not supported.
- **How a fix is delivered.** It lands on `main` first; the merged PR is
  labelled `backport release/<major.minor>` for each supported line it
  affects, `backport.yml` opens the cherry-pick PR, and once that is merged a
  maintainer runs **Prepare a release** with `patch` on the branch. Merging
  the prep PR tags and publishes the patch (see
  [What goes on a release branch](#what-goes-on-a-release-branch) and
  [Release candidate, GA, patch](#release-candidate-ga-patch)). An
  end-of-life line gets no fixes: upgrade to a supported release.
- **What that means at this cadence.** Releases go GA about weekly, sometimes
  more often, so N-1 may be supported for only days (0.28 was supported for
  three days in all). **Track the latest GA release**; treat N-1 as
  the window to upgrade in, not as a line to stay on.

`SECURITY.md` points here for the supported versions.

## What goes on a release branch

**Fix on `main` first, then backport.** Label the merged PR
`backport release/<major.minor>` (one label per target branch); `backport.yml`
opens the cherry-pick as a PR on that branch, as a draft carrying the conflict
if it does not apply cleanly. A conflict in `CHANGELOG.md` is expected — main's
`## Unreleased` is not on a GA'd branch — drop that hunk: a patch's changelog is
generated from the commit subjects it ships.

Only fix on the release branch directly when the code there no longer exists on
`main`: a maintainer adds the `release-direct` label to that PR, and its
description says why.

The `branch rules` check (`branch-rules.yml`) holds all of this: a PR into
`release/**` is a backport or prep PR the release bot opened, or labelled
`release-direct`; only the release tooling changes the version or `RELEASE`, on
any branch, and a cut PR into `main` counts only when the release bot or, for
the local fallback, a maintainer opened it.

## Changelog

Every PR with a user-visible change adds its entry under `## Unreleased` at the
top of `CHANGELOG.md` on `main`. The tooling owns the headings, and both sides
end up as the same `## 0.27.0 (<GA date>)`; nobody edits a heading by hand:

- at the cut, the cut PR closes `main`'s `## Unreleased` under
  `## 0.27.0 (unreleased)` and opens a fresh `## Unreleased` above it
  (`release-cut.yml` and the `scripts/cut-release.py` fallback alike);
- at GA, the GA prep turns the release branch's `## Unreleased` into
  `## 0.27.0 (<GA date>)` and opens a second PR, `release-date/0.27` into
  `main`, that rewrites `main`'s `## 0.27.0 …` heading to the same string.
  Merge it once the GA prep PR is merged and the `v0.27.0` tag exists.

So the two branches carry the same heading, and a backport touching
`CHANGELOG.md` conflicts only on `## Unreleased`. A patch's section lives only
on the release branch.

## Procedures

### Cut

Actions → **Cut a release** (`release-cut.yml`) on `main`, with the
`major.minor`, or:

```sh
gh workflow run release-cut.yml --ref main -f name=0.29                     # dry run: builds both commits, pushes nothing
gh workflow run release-cut.yml --ref main -f name=0.29 -f dry-run=false
```

With the release bot's token it pushes `release/0.29` (workspace at `0.29.0`,
`RELEASE` = `0.29.0-rc.0`, which `release-tag.yml` tags), creates the
`backport release/0.29` label, and opens the `release-cut/0.29` PR that moves
`main` to `0.30.0` and closes `main`'s `## Unreleased` changelog section under
`## 0.29.0 (unreleased)` (dated at GA, see [Changelog](#changelog)). Merge it. Tagging `v0.29.0-rc.0` adds the release to the
schedule above through the `release-schedule.yml` PR; merge that too.

`from` (`-f from=<rev>`) cuts from something other than `origin/nightly`.

Fallback, when the workflow cannot run: a maintainer runs
`python3 scripts/cut-release.py 0.29 [--dry-run] [--from <rev>]` from a clean
checkout with push access, Python ≥ 3.11, cargo, and `gh` authenticated. It
does the same with their own credentials: it creates the label first, pushes
`release/0.29` and `release-cut/0.29` together (`git push --atomic`), then
opens the PR. If it stops part-way, run the same command again: it resumes,
accepting a `release/0.29` that is its own cut commit on a `main` commit and
reusing an existing `release-cut/0.29` branch or open PR (a closed, unmerged
PR is replaced). Once the cut PR is merged, a rerun does nothing. The script and
`scripts/release_lib.py` are deleted once a release has been cut with
`release-cut.yml`.

### Release candidate, GA, patch

Actions → **Prepare a release** → choose the release branch as the ref and
`rc`, `ga` or `patch`. It moves `RELEASE`, writes the changelog (GA: the
`## Unreleased` section becomes `## 0.27.0 (date)`; patch: a new section listing
the commits since the last tag, above the newest version's), moves the whole workspace for a patch, and
opens a `chore(release): v…` PR from `release-prep/<major.minor>/<version>`.
A GA also opens `chore(release): date <version> in main's changelog` from
`release-date/<major.minor>` into `main` (see [Changelog](#changelog)). A
rerun of the prep force-updates both branches and reuses their open PRs.

**Merging it is the release.** On that push to the release branch:

- `release-tag.yml` tags `v<RELEASE>` and opens the GitHub Release (notes =
  that version's changelog section; an rc is a prerelease).
- `release.yaml` publishes the crates for a GA or patch (below).

After a GA, once the `v<major.minor>.0` tag exists, merge the
`release-date/<major.minor>` PR.

### Publish (crates.io)

Automatic, by `release.yaml`, on every push to `release/**`. It publishes only
when `RELEASE` is a GA/patch version equal to the workspace version, and only
the crates whose version is not on crates.io yet — so it is a no-op on every
other push, and re-running it after a failure resumes from the first missing
crate. Order is dependency order from `cargo metadata`; the run's log prints
the plan.

It authenticates with **crates.io Trusted Publishing only** — no registry token
is stored anywhere. Each crate is verify-built first (`cargo package`), then a
fresh 30-minute token is minted for its upload alone and revoked after it; a
failed upload is retried with a new token.

The workflow keeps the filename `release.yaml` because that is what each
crate's Trusted Publisher on crates.io names. Renaming it breaks publishing.

**A new crate** cannot be published this way: Trusted Publishing can only
publish to a crate that already exists and names this workflow as a trusted
publisher. `release.yaml` stops with an explanation. To add a crate:

1. An owner publishes its first version by hand:
   `git switch --detach v<version> && cargo publish -p <crate>`.
2. On crates.io → the crate → Settings → Trusted Publishing, add GitHub
   repository `affinidi/affinidi-trust-registry-rs`, workflow `release.yaml`,
   environment `release`.
3. Re-run `release.yaml` on the release branch for anything that waited on it.

### Schedule update

`release-schedule.yml` runs on `main`'s copy of the workflow whenever
**Tag a release** completes successfully, daily at 03:30 UTC (which heals a
missed run or any other drift), and from the Actions tab. It fetches the
tags, runs `python3 scripts/release_schedule.py --write` on `main` and, when
the table changed, force-pushes the `release-schedule` branch and opens (or
updates) the `docs(releases): update the release schedule` PR with the
release bot's token, so its checks run. It does not push when the open PR
already carries that table (a push would dismiss its approvals), and it closes
the PR when `main` already matches. Merge it like any PR.

The `release schedule` job in `checks.yaml` runs the generator's unit tests on
every PR into `main`, and compares the table with the tags only on a PR that
changes RELEASES.md or `scripts/release_schedule*.py`. Other PRs are never
failed by a new tag. A PR that does change RELEASES.md after a tag fails it
until the schedule PR is merged and the PR is updated from `main` (or it runs
`--write` itself). The job runs on PRs only, so it never holds `nightly` back.

It is a separate workflow triggered by `workflow_run`, not a job in
`release-tag.yml`, because a push to a release branch runs that branch's copy
of `release-tag.yml`, which for an existing branch predates any change on
`main`; `workflow_run` always runs the default branch's file.

To check locally (Python ≥ 3.11), with the tags fetched (`git fetch --tags`):

```sh
python3 scripts/release_schedule.py           # exit 1 and a diff if the table is stale
python3 scripts/release_schedule.py --write   # rewrite it
python3 -m unittest discover -s scripts -p 'test_*.py'
```

### End of life

Automatic: when a release goes GA, the schedule PR marks the release two
below it end of life, with that GA's date. Nothing is deleted: the branch,
its tags and its crates stay.

## Repository settings this relies on

Settings, not files:

- **Environment `release`** — `release.yaml` runs in it. Its deployment branch
  policy must allow `release/*` (it allowed only `main` while `main`
  published). Each crate's Trusted Publisher on crates.io names this
  repository, `release.yaml` and this environment.
- **Release-bot GitHub App** (`RELEASE_BOT_APP_ID`, `RELEASE_BOT_PRIVATE_KEY`
  secrets in the `release` environment, as `pipeline-rust` already uses — so
  `release-tag.yml`, `release-cut.yml`, `release-prep.yml` and `backport.yml`
  run their jobs in that environment, as does `release-schedule.yml`) —
  `release-tag.yml` creates tags with it (the `tags_managed` ruleset lets
  only that app and admins create tags), and `release-cut.yml`,
  `release-prep.yml`, `backport.yml` and `release-schedule.yml` push
  branches and open PRs with it (the enterprise does not allow `GITHUB_TOKEN`
  to open PRs, and a PR it opened would run no CI). The app needs contents and
  pull-requests write on this repository, and no ruleset may stop it
  creating or force-pushing the `release-cut/*`, `release-prep/*` and
  `release-date/*` branches it opens PRs from (a rerun of the prep
  force-pushes the last two). Its login,
  `affinidi-semantic-release[bot]`, is the one `branch rules` accepts cut,
  prep and backport PRs from.
- **Ruleset on `release/**`:** require a PR, require the `checks` jobs and
  `branch rules`, block force pushes and deletion.
- **Ruleset on `main`** (`Default_branch_managed`): add `branch rules` as a
  required check.
- **Ruleset on `nightly`:** block force pushes and deletion; only the release
  bot (which `nightly.yml` runs as), maintainers and admins may create or
  update it.
